## Step 1: data probe (H0–H2, ≤ 30 min of work)

1. For 5 recent boxwork drives (from MMGIS), query the raw-image API for Navcam left/right frames taken *during* the drive, not only at the stops.
2. For each drive record: number of stereo pairs, median spacing between consecutive pairs (from site/drive/pose fields), presence of camera models and attitude.
3. Write `vo/probe.json` and apply the rule in `nav.yaml`: **go** if ≥ 2 drives have ≥ 10 consecutive pairs at ≤ 2 m spacing with camera models; otherwise **no-go**.
4. N records D16 in the decision log by H2. **On no-go, stop.** WS9 runs on assumed parameter sets.

## Step 2: visual odometry (only on go, H2–H20)

1. Stereo feature matching (OpenCV ORB or SIFT), triangulation with the camera model (linearised CAHVOR → pinhole), frame-to-frame motion by PnP with RANSAC, accumulated along the drive.
2. Compare the endpoint with the MMGIS drive end; per drive: length, endpoint error, drift %, heading drift.
3. Write `vo/drift.json`; fit a Curiosity-calibrated set (σ_s, σ_b, ψ₀) and hand it to WS9 by H20, labelled "rover analogue: a rover is not an astronaut".

## Step 3: X9 (only after G2, if green and N is free)

At a drive end, project the stereo panorama to a top-down image and match it to the HiRISE ortho by normalised cross-correlation over rotation and translation; report error against MMGIS in `vo/orthomatch_*.json`. Cut first if anything else needs time.

## Tests

Two frames from the same pose give zero motion within tolerance; a known stereo baseline reproduces depth on synthetic points; the drift table lists every drive tried, failures included.
